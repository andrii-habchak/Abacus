  sheet ran `Task { await model.confirmApply() }`, and `confirmApply()` read
  `model.confirmation`. Tapping an alert button also sets the alert's `isPresented` binding to
  false, whose setter called `cancelConfirmation()`; the `Task` runs after that, found
  `confirmation == nil` and returned without writing anything (the sheet stayed open). The C7
  test called `confirmApply()` directly, so it never went through the binding.
  Fix: the alert captures the confirmation when it is built and the button calls
  `confirmApply(_ confirmation:)` with it (same pattern for the new rollback alert).
  Regression test `saveAndApplyThroughTheAlert` follows the alert's order (cancel via the

## Interpretations (for the orchestrator to confirm or move to DECISIONS)
1. **Edited since** = any of the rule-changed fields (category, type, accounts, amounts, refund,
   original amount) differs from what the rule set; such a transaction is left alone and
   counted as skipped. Other edits (note, date, description, event) do not block the rollback
   and are kept. A transaction whose old category/account no longer exists is also skipped.
2. Roll back undoes **every** recorded apply of the rule (newest first, so a transaction changed
   twice gets its oldest state back) and then forgets them; the rule itself stays. Rules applied
   on import are not recorded (only "Update existing transactions").
3. Deleting a rule deletes its records (CASCADE); the delete dialog says it can no longer be
   rolled back.
4. **Tester keeps its account picker**: it is an input of "Try a description" (per-account rules
   can only be tried with it), not a list filter; the list filter is now the category filter.
5. Search matches the rule in words, so "bigger than 100" finds amount rules.
