# C44 — Import History: move a batch to another account, Undo import label and states

State: done (awaiting merge)   ·   Branch: wp/C44-move-batch   ·   Updated: 2026-11-01

Owner requests (Import › History), all three built. Builds on the proposal in `docs/status/C41.md` (answer 3).

## Done

### 1. "Move to another account…"
- **Where.** Each History entry has "Move to another account…" next to "Show transactions" and "Undo import".
  It opens a sheet listing the batch's transactions in the review's row list: same columns (Status, Date,
  Description, Account, Amount, Category / action), same header sort (C41: ascending, descending, back to date
  order), same click / ⌘-click / ⇧-click selection, plus Select all / Select none. **Selected rows move**; all
  movable rows start selected.
- **Status per row.** "Moves" (selected; the Account column shows `Old → New`), "Stays" (not selected, dimmed) or
  "Can't move" with the reason in red under the category. Rows that move but have something to say carry a blue
  note: a transfer ("Only the “PKO private” side moves; “Cash” stays"), a linked refund ("Refund link kept"), a
  pending hold.
- **Target.** "Move to" is the shared searchable `AccountPicker` (C37/C40). It offers active, non-debt accounts in
  the batch's currency, the source excluded.
- **What happens** is spelled out above the button: N transactions move from A to B, categories, notes, events,
  attached records and links stay; how both balances change (signed sum of the moved rows); how many rows stay;
  that a re-import into B finds them as imported, that Undo import still removes them and that the move can be
  undone right after. The button is "Move N transactions".
- **After the move** an alert "Transactions moved" says what moved, with **Undo move** (moves the same
  transactions back; same atomic store call). A PKO file open in review whose target is one of the two accounts
  is rebuilt (as after an undo, C41).
- **Store** (`AbacusStore/Repositories/ImportBatchMove.swift`): `SQLiteImportStore.movePlan(_:)`,
  `move(_:txnIDs:from:to:)`, `fingerprintOwners(_:)`. The move is **one database transaction**; every selected
  transaction is checked again inside it and one refusal refuses the whole move (`ImportMoveError`).
  - Changes only the side on the source account (`accountID` / `toAccountID`); everything else (category, note,
    event, payee, attached records, `refundOfID`, the other side of a transfer, `importBatchID`) stays.
  - **Fingerprints.** A PKO fingerprint is `sha256(accountID | row parts)` and the parts are not stored, so the key
    for the new account cannot be computed without the file. The batch's PKO keys of the moved transactions are
    re-keyed to `moved:<old key>` (`ImportFingerprint.movedID`). On every PKO preview the pipeline parses the file
    once per account of its currency and looks up the moved keys (`NormalizedRow.movedFingerprints`); a hit counts
    as "Already imported" **only for the account the transaction is on now** (`ImportStore.fingerprintOwners`).
    So: a re-import into the new account → already imported; into the old account → new again (its key slot is
    free, so the import is not blocked) with the C41 yellow line "N rows … already imported into “New”"; moving
    again or back works (the moved key does not change). `alreadyImportedRows` counts moved rows by their current
    account. No migration.
  - **Batch ownership.** When nothing of the batch's own is left on the source account, the batch's `accountID`
    becomes the target (History, "Import into" checks after undo). If the batch is the latest PKO statement in its
    currency, the remembered "Import into" account (`statement|<currency>`) follows, when it pointed at the old
    account. Undo import keeps working: it deletes by `importBatchID` and fingerprints by `batchID`, both kept.
- **Refused rows ("Can't move")**, with the reason shown:
  - existing transactions the import linked to or settled (not the batch's own) — they stay;
  - rows no longer on the batch's account (account changed after the import);
  - debt legs and transfers to a debt account ("change it in Debts");
  - rows a **later import** touched (its fingerprint on them, e.g. a hold settled by a later statement, or a C38
    snapshot) — the reason names that file;
  - a transfer whose other side is the chosen target (it would become a transfer to itself) — only while that
    target is chosen; such rows leave the selection.
- **When the action is disabled** (help text says why): the batch is undone; not a PKO statement (a Saldo export
  spans many accounts); the batch has no transactions of its own (C41 count is 0).

### 2. "Undo import" label
"Undo import…" → "Undo import" in History, "Undo this import" → "Undo import" on the Done step, and the
confirmation dialog's button "Undo Import" → "Undo import". The confirmation dialog stays. There is no menu item
for it in the app (checked); the design prototype in `docs/design/` keeps its old text.

### 3. Undone batches
History entries of an undone batch keep their buttons but disabled ("Show transactions", "Move to another
account…", "Undo import"), show an "Undone" badge next to the date and the line "Undone — its transactions were
removed", greyed as before.

## Interpretations (please confirm)
- Only **PKO** batches can be moved; Saldo batches show the button disabled with the reason.
- **Transfers** created by the import (ATM withdrawals to Cash, transfers to own accounts) can move: only the
  statement's side changes, the other side stays (warned per row). A transfer onto its own other side is refused.
- **Linked refunds** move and keep their link (links are by id, across accounts allowed); warned per row.
- **Linked / settled existing transactions** stay and are listed as "Can't move" so it is visible what the
  import touched. Their link fingerprints stay on the old account's key.
- "**Already moved**" rows are not refused: a batch can be moved again (and back); rows whose account was changed
  by hand are refused as "no longer on" the account.
- A **partial move** (some rows deselected or refused) leaves the batch on its old account; only a full move
  re-assigns the batch and the remembered "Import into" account.
- **Undo** of the move is offered once, right after it (alert button), not in History; later the same result is
  reached by moving the rows back with the same action.
- Moving a batch whose rows were imported, moved, imported again into the old account and then moved again is
  refused ("would be there twice").

## API
- AbacusDomain: `Model/ImportBatchMove.swift` (`ImportFingerprint.movedID/movedPrefix`, `FingerprintOwner`,
  `ImportMoveRefusal`, `ImportMoveNote`, `ImportMoveCandidate`, `ImportMovePlan`, `ImportMoveResult`,
  `ImportMoveError`); `ImportStore.fingerprintOwners(_:)` (default `[:]` for fakes).
- AbacusImport: `NormalizedRow.movedFingerprints`; `ImportPipeline.movedKeys(of:rows:currency:accounts:)` used by
  `preview`; `RowAnalyzer` checks moved keys; `alreadyImportedRows` counts moved rows.
- AbacusFeatures: `Import/ImportMove.swift` (`ImportMoveModel`; wizard `moveSheet`, `moveNotice`, `lastMove`,
  `canMove`, `moveUnavailableReason`, `requestMove`, `startMove`, `confirmMove`, `startUndoLastMove`,
  `cancelMove`); `Activity.moving`; `ImportWizardDependencies.movePlan/moveBatch` (wired in `live`).
  `ImportRowSort.toggled/sorted`, protocols `ImportRowSorting` / `ImportRowSelecting` (the review model and the
  move model share the header and the selection helper).
- App: new `Import/ImportMoveSheet.swift`; `ImportRowCells` split out of `ImportRowView` (shared by both lists);
  `ImportRowsHeader` and `importSelect` take the protocols; History entry, sheet and alert in `ImportView.swift`.
