# C42 — Rules: special letters, rules from review resolutions
State: done (awaiting merge)   ·   Branch: wp/C42-rules-text   ·   Updated: 2026-11-01

## 1. Special symbols in rule matching (suggested solution, implemented)

**Cause.** Rule text was compared after `folding(.caseInsensitive, .diacriticInsensitive)`. That only removes
combining marks, so Ą Ć Ę Ń Ó Ś Ź Ż fold to ASCII ("URZĄD" matches "URZAD") but **Ł/ł has no decomposition** and
stayed "ł". "ZAKŁAD UBEZPIECZEŃ SPOŁECZNYCH" therefore never matched a rule typed with plain L. Same for ø, đ, ß,
æ, œ, þ, ħ, ı.

**Solution.** New `AbacusDomain/Model/TextFolding.swift`:
- `TextFolding.fold` first maps the letters without a decomposition to their usual ASCII spelling
  (Ł→L, ł→l, Ø→O, ø→o, Đ→D, đ→d, Ð→D, ð→d, ß→ss, ẞ→SS, Æ→AE, æ→ae, Œ→OE, œ→oe, Þ→TH, þ→th, Ħ→H, ħ→h, ı→i,
  Ŀ→L, ŀ→l), then applies the case + diacritic folding.
- `RulePattern.normalized` (used for the pattern **and** the transaction text, search boxes, derived patterns)
  uses it, so the folding is symmetric: the pattern may be typed with or without the special letters.
- The same fold is used by fuzzy duplicate words (`DescriptionSimilarity`), refund and transfer counterpart text
  search. Not touched (kept as is on purpose): debt person names (`Debts.swift`) and `RefundRepository.fold`
  (store side).
- **Replacement character.** A U+FFFD in the (folded) text matches exactly one character
  (`TextFolding.matches`, used by contains / starts with / equals): "URZ\u{FFFD}D SKARBOWY" matches "URZAD SKARBOWY"
  and "URZĄD SKARBOWY". Guard to keep it predictable: a match whose window has fewer real characters than
  wildcards (less than half real) is rejected, so text of replacement characters does not match everything,
  and "Z\u{FFFD}\u{FFFD}" does not match "ZUS" while "Z\u{FFFD}S" does. Text without U+FFFD takes the old plain path.
  A literal "?" is **not** a wildcard (it is a normal character; a "?" substitute cannot be told from a question mark).
- **Nothing stored changes.** Rules store the typed text, fingerprints do not use this folding (they are untouched);
  a stored pattern with "ł" folds to the same "l" as the text, so old rules keep matching. New learned patterns are
  stored in the folded form ("l" instead of "ł").

Tests: `TextFoldingTests` (Polish pangram, ZUS both directions in contains / starts with / equals, old patterns,
replacement characters, guard, plain text).

## 2. Rule suggestion for review resolutions

**Before.** A category pick on a normal row is saved as a rule by default ("Will be saved as a rule", "Don't save"
button, bulk "Save rules" sheet). The resolutions on Needs review cards never produced a rule.

**Now** (cards with reason *Unknown operation type*; the owner's case): once the card is resolved,
- **Expense / Income with a category** (of the sign's kind) → category rule,
- **Transfer to my account** → transfer rule (`transferAccountID`),
- **Debt…** → "Transfer to debt of <person>" rule (`debtPersonName`),
are proposed like category picks: the card shows "Will be saved as a rule “text” → target" with "Don't save" /
"Save as rule"; the bulk Category / Account / Debt actions open the existing "Save rules" sheet (text editable,
tick to save; the sheet now shows the action instead of only a category). The rule text is derived as for categories
(`RulePattern.derive`, or the edited one) and is saved on commit with the rest (`CommitBuilder`), `origin = imported`.
`RuleProposal` carries the action (`LearnedAction`); `PreviewRow.learnedAction` says what a rule would do.

**Resolving later rows.** Before, only a category rule let an unknown-type row skip review. Now a transfer rule
(when its amount on the other account is known) or a debt rule does too, so the saved rule is useful next import.

**Not expressible, so no suggestion** (documented, deliberate):
- *Skip* (a rule cannot exclude a row), *Pair with …* (depends on the other row), a record without category,
  a record of the other kind than the sign (reversal / refund, a rule only resolves rows of the sign's kind).
- Other review reasons (unpaired transfer half, transfer amount unknown): a payee rule would also hit ordinary rows of
  that payee, so no suggestion (can be added later).
- No suggestion when an enabled rule already matches the row.

Interpretations: the rule is on by default, as for categories; rules from resolutions are not applied to the other
rows of the same import (the user decides each card); unknown-type resolutions only.

Tests: `ReviewRuleSuggestionTests` (category, transfer, debt rules proposed and saved; not-expressible choices;
toggle and edited text; no duplicate when a rule matches; learned transfer rule resolves the next import);
`ImportReviewTabTests` bulk category now expects the sheet.
