# N4 — Database encryption research (document only)

_Researched 2026-11-03. No code written, nothing under `~/Library/Application Support/Abacus/` touched.
Facts marked **[verified]** come from the primary source linked next to them; **[unverified]** means
I found no primary source or could not test it here._

## Summary

| Option | Protects against | Cost / risk | Verdict |
|---|---|---|---|
| **A. FileVault only** (status quo) | Lost or stolen Mac, removed disk, a copy of the file taken while the Mac is off or the user logged out | None. No key to manage. Does **not** protect while the owner is logged in (other processes of the same user, a stray copy of the file on another disk) | **Recommended now**, plus a check that FileVault is on |
| **B. SQLCipher (whole-file AES-256)** | The same, plus the file and every copy of it (backups, a copy in iCloud Drive) | GRDB needs a **fork** for SwiftPM, SQLiteData needs one too, Xcode has no trait support; key must live in the Keychain, which an **ad-hoc signed** app and the separate `abacus-mcp`/`abacus-import` binaries cannot use without repeated prompts; key loss = data loss | Not now. Revisit when Developer ID signing exists (iOS/sync start) |
| **C. Field-level encryption** | Selected columns only | Breaks `SUM`/`GROUP BY`/`LIKE`, the core of reports (D6), search and import dedupe; metadata (dates, accounts, counts) stays readable | Rejected |
| **D. Encrypt the copies only** (backup/export files, N1's optional second folder) | A backup that leaves the disk (iCloud Drive, external disk) | Small, independent of the live database; passphrase typed by the owner, no Keychain | **Optional follow-up** to N1, cheap compared with B |

**Recommendation:** keep the live database unencrypted and rely on FileVault (A). N7 app lock is a
UI gate, not encryption. Revisit B once the app is Developer ID signed and iOS sync is being
built. If backups go off the machine before that, do D.

## 1. Context that decides the answer

- Single user, offline-first (R-NF-1), personal Mac. The threat worth a defence is a lost or stolen
  Mac and a backup copy that leaves the disk. Malware running as the same user is out of scope for
  any local-file scheme: it can ask for the Keychain item or read process memory.
- The app is **ad-hoc signed** (`CODE_SIGN_IDENTITY: "-"` in `project.yml`); no paid Apple account.
- Persistence today: `AbacusDatabase.open(at:)` builds a plain `Configuration()` and opens a
  `DatabasePool` (WAL) at `~/Library/Application Support/Abacus/abacus.sqlite`; the location can be
  moved (`DatabaseLocation`). GRDB 7.11.1 and SQLiteData 1.12.1 are pinned in
  `AbacusKit/Package.resolved`. Nothing in the code uses `SyncEngine` yet.
- Four other places open or copy the file and would all have to learn a key: `DatabaseLocation.copy`
  / `verify` (opens `DatabaseQueue(path:)` and the copy without a key), `Backup.export`/`restore`
  (`ATTACH DATABASE` of a backup), `abacus-import`, and the planned `abacus-mcp` (N2).

## 2. Option A — FileVault only

- FileVault encrypts the whole internal volume with AES-XTS; without login credentials or the
  recovery key the volume stays encrypted, and on Apple silicon key handling happens in the Secure
  Enclave **[verified]**
  ([Apple Platform Security: Volume encryption with FileVault](https://support.apple.com/guide/security/volume-encryption-with-filevault-sec4c6dc1b6e/web)).
- Not covered **[verified by absence]**: that article does not describe what protects data **after
  login**. In practice every process of the logged-in user can read the file; that is the gap B closes
  only partly (see §1).
- Copies that leave the volume (N1's second folder, iCloud Drive, an external disk) are **not** under
  the volume's FileVault: an external disk is only protected if the owner encrypted it, iCloud Drive
  is encrypted on Apple's servers but not end to end unless Advanced Data Protection is on
  ([Apple: iCloud data security overview](https://support.apple.com/en-us/102651): iCloud Drive is in
  the list of categories that need ADP for end-to-end encryption **[verified]**).
- Effect on backups, MCP, import, performance, CloudKit: none.

**Action for the owner:** check System Settings › Privacy & Security › FileVault is on (can be
shown in the app's Settings as a read-only hint; no code needed for the research).

## 3. Option B — SQLCipher

### What it is
- AES-256 in CBC mode with a per-page HMAC-SHA512; PBKDF2-HMAC-SHA512 with 256,000 iterations when
  given a passphrase, or a raw 32-byte key as `x'…'` hex with no derivation; 4096-byte pages; random
  salt in the first 16 bytes of the file. Main file, rollback journal and **WAL page data are
  encrypted**; statement journals too, but other transient (temp) files are not, so file-based temp
  storage should be disabled **[verified]**
  ([SQLCipher design](https://www.zetetic.net/sqlcipher/design/)).
- `PRAGMA key` must run first on every connection; a wrong key is only detected on the first read
  (e.g. `SELECT count(*) FROM sqlite_master`). `PRAGMA rekey` re-encrypts every page but **cannot
  encrypt an existing plaintext file**: that is `sqlcipher_export()` into an attached database
  opened with a `KEY`. `cipher_plaintext_header_size` exists for iOS WAL files in shared containers
  **[verified]** ([SQLCipher API](https://www.zetetic.net/sqlcipher/sqlcipher-api/)).
- A raw key avoids the 256k-iteration PBKDF2 cost on each connection open (a `DatabasePool` opens
  several connections); with a passphrase every connection pays it **[unverified as a measured
  number; the mechanism follows from the documented KDF]**.

### With GRDB / SQLiteData
- GRDB API: `try db.usePassphrase("…")` inside `config.prepareDatabase`; `db.changePassphrase` (pool:
  `barrierWriteWithoutTransaction` then `invalidateReadOnlyConnections()`); plaintext → encrypted via
  `sqlcipher_export`. If the passphrase comes from the Keychain and becomes unavailable, a
  **database pool can fail when it opens new connections**, a queue keeps working **[verified]**
  ([GRDB README › Encryption](https://github.com/groue/GRDB.swift#encryption)).
- **SwiftPM is the catch.** GRDB 7.10.0 added SQLCipher via SwiftPM, but you must **fork GRDB and
  edit `Package.swift`** (instructions in comments marked "GRDB+SQLCipher"); no official fork exists,
  the author expects forks to be needed "for several years", derived projects such as SQLiteData
  need forks too, and Xcode does not yet support package traits, which are what would let GRDB link
  SQLite *or* SQLCipher **[verified]**
  ([GRDB 7.10.0 announcement](https://forums.swift.org/t/grdb-v7-10-0-android-linux-windows-and-sqlcipher-swiftpm/84754)).
  Abacus gets GRDB through SQLiteData, so this means maintaining forks of **two** packages
  (or overriding the GRDB dependency of SQLiteData) and rebasing on every update.
  The CocoaPods route does not fit (the project is SwiftPM + xcodegen).
- SQLiteData has no SQLCipher trait; its docs only mention SQLCipher as an example of a custom SQLite
  build for which the `SuppressPlatformSQLiteAvailability` trait can be enabled, "only if the
  embedded SQLite supports the features you use" **[verified]**
  ([SQLiteData Traits](https://github.com/pointfreeco/sqlite-data/blob/main/Sources/SQLiteData/Documentation.docc/Articles/Traits.md)).
  Whether SQLiteData 1.12.1 compiles and runs against a SQLCipher-linked GRDB fork **[unverified —
  needs a spike]**.
- Third-party prebuilt forks exist (e.g.
  [session-foundation/session-grdb-swift](https://github.com/session-foundation/session-grdb-swift),
  GRDB 7.4.1 + SQLCipher 4.7.0 per its README at the time of search) but lag behind GRDB 7.11.1 and
  add a supply-chain dependency for a finance app. Not recommended.

### CloudKit sync (`SyncEngine`, D6/D18/D19)
- SQLCipher encrypts the **local file only**. `SyncEngine` sends record fields to CloudKit; local
  encryption neither helps nor hinders what Apple stores. The SyncEngine requirements (UUID keys,
  only `CASCADE`/`SET NULL`/`SET DEFAULT`, no unique constraints beyond the key, additive migrations)
  concern schema, not storage **[verified]**
  ([SQLiteData CloudKit sync article](https://github.com/pointfreeco/sqlite-data/blob/main/Sources/SQLiteData/Documentation.docc/Articles/CloudKitSync.md)).
  That article says nothing about encryption or SQLite builds, and keeps sync state in a separate
  *metadatabase* attached through `Configuration.prepareDatabase` (its file location is not stated).
  **[unverified]**: whether the metadatabase file is encrypted by the same key (it would need its own
  `usePassphrase`), and how `SyncEngine` behaves if it cannot open it.
- Server side: third-party app data in CloudKit is encrypted in transit and on the server, and
  end-to-end only for "CloudKit encrypted fields and assets" with Advanced Data Protection on
  **[verified]** ([Apple](https://support.apple.com/en-us/102651)). Whether `SyncEngine` writes
  its fields as CloudKit *encrypted* fields **[unverified; not mentioned in its article]**. For sync,
  this is the question that matters for privacy, not SQLCipher.
- iOS later: the same key problem moves to the iPhone, where the Keychain is better behaved (see §6).
  `cipher_plaintext_header_size` is only needed for shared containers/extensions.

### Backups (N1)
- N1 makes file copies. With SQLCipher a snapshot made with SQLite's online backup is **encrypted
  with the key of the destination connection**; `DatabaseLocation.copy` and `Backup.export` currently
  open the destination as a plain `DatabaseQueue(path:)`, so they would write a plaintext copy (or
  fail), and `Backup.restore`'s `ATTACH DATABASE ? AS backup` has no `KEY`. **[unverified; the
  exact backup-API behaviour with differing encryption needs a test]** — each of these would need
  a key-aware variant, and the pre-migration snapshot and the 14/6/3 retention set all depend on the
  one key staying valid (`rekey` makes every older snapshot need the old key).
- Positive: an encrypted database makes backups in iCloud Drive or on an external disk safe without
  extra work. That benefit is also achievable with option D.

### MCP server (N2) and `abacus-import`
- `abacus-mcp` is a **separate process** and a separate binary with its own code identity. It would
  have to read the key: from the Keychain (a different binary reading an item created by the app
  gets its own authorization prompt, and an ad-hoc binary has no stable identity, see §5), from an
  environment variable or a file (weakens the scheme: the key is then readable by whatever can read
  that), or by asking the running app over a local channel (the heavier single-writer design the
  roadmap already mentions). The same applies to `abacus-import`.
- `PRAGMA data_version` is a SQLite per-connection counter that changes when **another connection**
  commits and is unchanged by commits on the same connection **[verified]**
  ([SQLite PRAGMA](https://sqlite.org/pragma.html#pragma_data_version)). Nothing in it depends on
  how pages are stored, so polling should work on an encrypted file once the polling connection has
  keyed it **[unverified for SQLCipher; the page doesn't discuss it]**. A read-only connection must
  still run `PRAGMA key` first.
- The WAL page data is encrypted (above), so the `-wal` file is no leak. The `-shm` index holds no
  page data **[unverified in the SQLCipher docs; SQLite property from general knowledge]**.

### Performance
- SQLCipher adds per-page AES + HMAC work and a KDF at open. The SQLCipher design page makes **no
  numeric statement** about overhead **[verified]**; any figure I could quote would be from
  non-primary sources, so none is given. For R-NF-2 (20 000 transactions, filter < 200 ms) the
  expectation is a modest cost on cold reads, but it must be **measured** with the existing
  large-data timing test (which already flakes in a full parallel run, N3) before B is adopted.

## 4. Option C — field-level encryption

Encrypt amounts, descriptions or IBANs with CryptoKit before storing. Reports are `SUM`/`GROUP BY`
over amounts and dates in SQL (D6), search is `LIKE` over descriptions, import dedupe uses
fingerprints over the same fields (D18), `UNIQUE` constraints and indexes need plaintext. Encrypting
the useful columns forces loading and decrypting rows into Swift (R-NF-2 at risk) and still leaves
dates, account links, row counts and structure readable. It also does nothing for the Keychain
problem: the key still has to live somewhere. Rejected.

## 5. The key-management problem

### Why ad-hoc signing breaks a Keychain-held key
- A macOS app is identified by its **designated requirement (DR)**. "Ad hoc signed code, called Sign
  to Run Locally by Xcode, has a DR but it's tied to that specific version of the code … macOS can't
  reliably track the identity of the code"; with a Developer ID the default DR is anchored on Apple,
  the signing identifier and the Team ID, so it survives updates **[verified]**
  ([TN3127: Inside Code Signing: Requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)).
  The note lists "the keychain presents unexpected authorization alerts" among the symptoms.
- Keychain item access is checked against the creating app's identity: in an Apple developer forum
  thread an Apple engineer states the check is based on the DR, and that later versions must satisfy
  the DR recorded when the item was created ([thread 98484](https://developer.apple.com/forums/thread/98484)).
  **[Not an official document; and the exact behaviour for ad-hoc rebuilds on macOS 26 I could not test
  here.]** The expected result for Abacus: each rebuild gets a new DR, so the system asks for access
  to the item again (the "keeps asking" the owner described). Easy to confirm: run
  `codesign -d -r- Abacus.app` on two builds and compare.
- The same holds for the `abacus-mcp` and `abacus-import` executables: separate binaries, ad-hoc
  signed, so each is a separate identity that must be allowed per build.
- **Developer ID** (paid Developer Program) gives a stable DR and also enables the Data Protection
  Keychain with an access group shared by app and tools, and Secure-Enclave-bound keys. Whether an
  access group is usable for a command-line tool outside an app bundle **[unverified]**.
- Cheaper stopgap: a free self-signed certificate gives a stable DR across rebuilds (the Keychain
  prompt stays away) but no notarisation; the same source above notes it is a workaround, and I
  could not confirm it with Apple documentation **[unverified]**.

### Where could the key live (all require B)
| Place | Works with ad-hoc signing | Notes |
|---|---|---|
| Keychain item (generic password) | No: prompts after each rebuild | Fine with Developer ID. Biometric (Touch ID) protection of the item needs an access-control flag and normally a properly signed app **[unverified for ad-hoc]** |
| Passphrase typed by the owner at launch | Yes | PBKDF2/Argon-style derivation; no Keychain; fits "unlock" in N7; usable by `abacus-mcp` only if prompted too or passed in, so MCP becomes awkward |
| Key file next to the database | Yes | Defeats the purpose except against a disk copy of the database alone |
| Secure Enclave key wrapping the DB key | No, needs signing/entitlements | Device-bound: the encrypted database or its backups cannot be restored on another Mac without a recovery key |

### Key loss and recovery
- SQLCipher has no back door: **lose the key, lose the database**, and every backup made with it.
  A Keychain item is lost with a reinstalled OS, a wiped Mac, or a changed signing identity that
  cannot read the item. With a passphrase it is lost when forgotten.
- Mitigations the design would need: a printed/stored **recovery key** (the raw 32-byte key shown
  once, kept on paper by the owner), a documented rekey procedure (`PRAGMA rekey`; a pool needs the
  barrier steps above), `sqlcipher_export` to decrypt on demand, and at least one backup readable
  with the recovery key. Without these, B adds a way to destroy the only copy of the data, which
  outweighs the benefit for a single-user offline app whose threat is a stolen laptop (already covered
  by FileVault).
- FileVault itself has a recovery key; losing it is the same class of risk, already accepted.

## 6. Recommendation

1. **Now: option A.** Keep the database unencrypted at the application level; rely on FileVault.
   Show a read-only "FileVault is on" hint in Settings if wanted (needs a separate small WP; not
   part of N4). Add nothing to `Package.swift`.
2. **Do not adopt SQLCipher while the app is ad-hoc signed.** It needs two package forks, breaks the
   stability of the Keychain item on every rebuild, forces the MCP server and importer to solve key
   delivery, and adds key-loss risk, for a threat FileVault already covers.
3. **Revisit B (spike first) when both are true:** the owner has a paid Developer account and the app
   is Developer ID signed (roadmap §2 prerequisites for iOS/sync), and an encrypted copy is needed on
   iPhone or iCloud. The spike should answer: SQLiteData 1.12.x on a SQLCipher GRDB fork in Xcode;
   `data_version` and a read-only connection under a key; the SyncEngine metadatabase; backup-API
   behaviour with a keyed destination; timing against R-NF-2. Use a raw 32-byte key (no KDF per
   connection), held in the Keychain under the Developer ID DR, plus a printed recovery key.
4. **Optional, earlier and independent (option D):** if N1's second folder points at iCloud Drive or
   an external disk, encrypt the *copy* (CryptoKit AES-GCM, key from a passphrase typed when creating
   and restoring; no Keychain). The live database and the other tools stay unchanged.

## 7. What the N7 app-lock lane should assume

- N7 is a **UI lock only**: the database file stays unencrypted and readable by other processes.
  Document that honestly in Settings help (the lock hides content in the window; FileVault protects
  the disk).
- Use `LocalAuthentication` (Touch ID with password fallback) as a gate on the window. Nothing in the
  lock may depend on a Keychain item or on any database key; it must keep working with an ad-hoc
  signed build and with the identity changing on every rebuild. Persist only the settings (on/off,
  idle minutes), not a secret.
- Design the lock/unlock state as an app-level model (e.g. `isLocked`), with the database opened as
  today, so that a later encryption step can **hook in at unlock** (derive or fetch the key, then open)
  without redoing N7's UI. Do not open the database lazily at unlock in N7 itself.
- Do not couple N7 to `abacus-mcp`/`abacus-import`: they open the file directly and are not blocked by
  the app lock (say so in the README/Settings text). If the owner wants MCP blocked while locked,
  that is a separate decision tied to the encryption/key delivery question above.
- Reconsider when B is adopted: then unlock = obtain the key (biometric-protected Keychain item,
  Developer ID signed) and the lock becomes real protection.
