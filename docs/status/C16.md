# C16 — PKO pending holds shown as income (R-IMP-PKO-2)
State: done (waiting for merge)   ·   Branch: wp/C16-pending-sign   ·   Updated: 2026-10-30

## Bug (owner-confirmed)
In the import wizard, PKO card holds ("Pending at the bank" rows) showed as income (`+zł`,
green) instead of expenses.

## Root cause
`PKOParser` derived a hold's direction from the sign of `Kwota`, like a settled card payment:
`case .hold, .cardPayment, .webPayment: kind = .expense; isRefund = isCredit`. A `Blokada` row
whose amount carries no minus sign (unsigned or `+`) therefore became an expense *refund*, i.e.
money in (`NormalizedRow.flow == .in` → `PreviewRow.isInflow` → green `+` amount). The wizard's
"Pending at the bank" detail only appears for `isPending` rows, so this was the only path that
shows a pending row as income.

Checked on the real export in `samples/private/` (counts only): its two `Blokada` rows are
signed `-` and import correctly as pending expenses (probed through the full preview), so the
owner's case comes from an export whose hold amounts are not negative. The newer exports outside
`samples/private/` could not be read from this lane; a copy of the newer PLN export in
`samples/private/` would let the real-data test confirm it.

## Fix
- `PKOParser`: a hold is always money out — `kind = .expense`, `isRefund = false`, amount = the
  magnitude, whatever the sign. PKO has no pending credit type: a card refund arrives as a settled
  `Płatność kartą` with a positive amount and still becomes a refund (inflow); transfers and
  unknown types keep sign-based direction.
- The hold fingerprint still uses the file's amount text unchanged, so holds imported earlier
  are still recognised as "Already imported".
- `RowAnalyzer` settle match (R-IMP-PKO-2) no longer requires `!hold.isRefund`: a hold stored as
  a refund by an older build is still matched by its settled payment.
- `CommitBuilder` settle sets `isRefund = false` on the upgraded hold, so settling repairs such a
  hold.
- `docs/import/pko-format.md`: the hold row's direction rule.

## Existing data
- The app database (`~/Library/Application Support/Abacus/abacus.sqlite`) was checked read-only,
  counts only: 2 pending holds, both `isRefund = 0` → **no wrong-sign holds stored; no repair
  needed now.**
- If a wrong-sign hold had been committed: it is repaired automatically when its settled payment
  is imported (above). Not covered: a wrong-sign hold whose settled payment was already imported
  as a separate expense (the settle match skipped it), or one that never settles — the user
  deletes it, as with any released hold.
- **Proposed, not added** (migrations are shared files, orchestrator only): an optional
  migration `UPDATE "txns" SET "isRefund" = 0 WHERE "isPendingAtBank" = 1 AND "type" = 'expense'
  AND "isRefund" = 1 AND "source" = 'pko'`. Low risk (no import path creates pending refunds),
  but unnecessary for the owner's current database.

## Tests
`AbacusImportTests/PendingHoldSignTests.swift` (synthetic):
- a hold signed `-`, `+` or unsigned parses as a pending expense, not a refund; fingerprint
  keeps the file text;
- a positive card payment stays a refund (inflow), an incoming transfer stays income;
- pipeline: an unsigned hold previews as money out, commits as a pending expense, and the later
  settled card payment settles it (no new transaction, balance unchanged);
- a hold stored as a refund by an older build is settled and repaired, not duplicated.

Verified: `swift test` with `ABACUS_SAMPLES` (705 tests, real-data suites ran) and the macOS app
build.
