# C38 — Import: the other side of a transfer to an own account in another currency
State: done (awaiting merge)   ·   Branch: wp/C38-transfer-counterpart   ·   Updated: 2026-10-31

Owner-confirmed problem: a PKO row whose counterparty account is one of the user's own accounts in
another currency (a USD account sending to the PLN account) got the review reason
`.transferAmountUnknown`, and "Transfer to my account" then failed ("the amount in X is unknown").
Approved design, all three parts, is built.

## Behaviour
1. **Find the other side…** Choosing "Transfer to my account" (review card, the card's account
   picker, the bulk bar Account action with one row selected, and "Change…" under a chosen transfer)
   for a row whose amount on that account the file does not give opens a sheet:
   - Transactions of the other account within ±5 days of the row, opposite direction (outgoing row ↔
     money in, incoming row ↔ money out; income, expense refunds, expenses, income reversals all
     count), ranked by how close the amount is to the row's amount at the day's rate (the latest known
     rate when the day has none), then by date distance. Each line shows the implied rate and the
     deviation from the expected amount. Candidates that cannot be absorbed are listed last with the
     reason and cannot be chosen. A search text widens the window to ±60 days and filters by
     description, note and amount.
   - Choosing one makes ONE transfer with both real amounts (`amountMinor` = the outgoing side,
     `toAmountMinor` = the incoming side) and absorbs the found transaction (see "Absorbing").
2. **No counterpart yet** (same sheet): type the received amount (comma or dot, positive, the other
   account's currency), or "Estimate at the NBU rate" (disabled when no rate is known). Both make a
   transfer with both amounts. The estimate flags the transfer (`txns.isEstimatedTransferAmount`); the
   Transactions list shows "estimated amount" after the received amount on the transfer
   ("→ zł 400.00 · estimated amount"). A typed amount is not flagged. Editing an estimated transfer in
   the editor keeps the flag until an amount or an account changes.
3. **Later import.** A row on the other account (new income/expense without attached records, or a
   Needs review row with reason "transfer amount unknown") that matches an existing ESTIMATED transfer
   (flagged; the row's account is a side of it; money in for the receiving side, money out for the
   sending side; ±5 days; amount within 5 % of the estimate) shows "Looks like the other side of the
   transfer on <date> · <amount> (estimated)" with Accept / Not this (Transactions tab and review
   card). Accept links the row: it sets that side of the transfer to the real figure, clears the flag,
   stores the row's fingerprints on the transfer, creates no second transaction; the row counts as
   linked ("Completes transfer", status Already imported, summary "N transfers with an estimated amount
   completed"). Not this: ordinary row, no offer again on this preview; Undo brings it back. Transfers
   that are not flagged are never matched. One transfer is offered to one row only.

## Absorbing (design)
- The found income/expense is **converted in place** into the transfer (same id, like `.convert` /
  `pairExisting`), not deleted and re-inserted: its fingerprints stay, the row's fingerprints are added
  to it (re-importing the same statement shows the row as already imported). When the transaction is
  on the receiving account (outgoing row) the transfer takes the row's date, booked day, description
  and note; for an incoming row it keeps its own (the outgoing side's) date.
- **Undo.** `ImportCommit.absorbedOriginals` / `completedOriginals` carry the transactions as they were;
  the store validates them inside the commit and writes the transaction as it is *at commit time* to the
  new table `importTxnSnapshots` (JSON of the `Txn`, cascade-deleted with the batch). Undo of the batch
  restores each (skipped when it was deleted since) and deletes the snapshots. Only absorbing and
  completing an estimate use it; `pairExisting`, links and settled holds keep their old undo behaviour
  (field changes stay).
- **Refusals** (`TransferAbsorb.refusal`, shown in the sheet and enforced by the commit, which fails as a
  whole with `TransferCounterpartError.cannotAbsorb`): already a transfer, balance correction, attached
  records, a refund link either way, debt (`debtRecordID`, or an account linked to a debt), archived
  account, no longer exists. A row with attached records cannot absorb (the conversion would drop them).
- A commit that completes an estimate fails with `estimateGone` when the transfer is no longer flagged.

## Schema v16 ("v16: estimated transfer amounts")
`txns.isEstimatedTransferAmount INTEGER NOT NULL ON CONFLICT REPLACE DEFAULT 0` (added only when
missing) and `importTxnSnapshots(id PK, batchID → importBatches ON DELETE CASCADE, txnID, json)`
(`CREATE TABLE IF NOT EXISTS`, index on batchID), STRICT like the other tables. Append-only,
CloudKit-safe (no UNIQUE, only CASCADE), safe to run again. `Txn` is now `Codable` (snapshot encoding).

## Interpretations (please confirm)
- Absorbing converts in place instead of delete + insert (same observable result: one transfer, the
  other statement's fingerprints kept, undo brings the income back).
- A typed amount is not flagged as estimated; only the NBU estimate is (as specified).
- Candidate window ±5 days; a search text widens it to ±60 days (the spec gave no search window).
- "Rows of this file" as candidates (other statement in the same import) is not built: Saldo halves are
  already paired by the existing pairing, and a PKO file never has rows of two accounts. If a
  multi-file import is built later, the counterpart search over the file's rows is the extension point.
- The estimate uses the converter's day rate with the latest known rate as fallback, so a transfer on a
  day before the first stored rate still gets an estimate.
- Bulk Account: a row that needs its other side is not changed by a multi-row bulk action; with exactly one
  row selected the sheet opens, otherwise the bar says to select one row.
- The per-row Transactions-tab account action does not exist in the build (bulk Account and the review card
  are the entry points); "Change…" under a chosen transfer reopens the sheet.

## Proposed text for the shared docs (orchestrator)
- **R-IMP-PKO-3 (addition):** "When the other own account is in another currency and the file does not
  give the amount received there, the user may make the row a transfer by (a) choosing the transaction
  already imported from the other account's statement (±5 days, opposite direction, ranked by the amount
  at the day's rate), which becomes the transfer, (b) typing the amount, or (c) estimating it at the day's
  rate; an estimated transfer is marked until a later import row on the other account (±5 days, ±5 % of the
  estimate) is accepted as its real figure."
- **R-TX-5 (addition):** "A transfer may be marked 'estimated amount' (received amount estimated at the day's
  rate); the mark clears when an import completes it or the user edits an amount."
- **Decision D-new:** "Absorbing an existing income/expense into a transfer converts it in place; the batch
  keeps a snapshot (`importTxnSnapshots`) so undo restores it. Refused for attached records, refund links,
  debts, balance corrections, transfers and archived accounts."
- **Schema:** v16 as above. Mention in the migration list of `PLAN.md` §1.

## Limitations
- The headless `abacus-import` tool has no counterpart repository: it never offers or completes anything and
  still blocks on a "Transfer to my account" without an amount (`acceptingDefaults` records such rows by
  sign as before).
- Undoing the earlier batch that created an absorbed transaction deletes the transfer too (the transaction
  keeps its original batch id); undoing the absorbing batch first restores it.
- The estimate offer is looked up once per eligible row when the preview is built and after an account
  remap (read-only).
- Rows with attached records are neither offered an estimated transfer nor can absorb a transaction.
