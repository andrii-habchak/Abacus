# C30 — Refund links
State: done (awaiting merge)   ·   Branch: wp/C30-refund-links   ·   Updated: 2026-10-30

Owner-approved design: a refund transaction is linked to the original expense so a returned
purchase cancels the expense in reports. Lane C31 works on the import wizard in parallel; this lane
keeps out of `AbacusImport/` and the import views.

## Design (as built)
- **Schema:** migration v15 adds `txns.refundOfID TEXT` (nullable, no foreign key, no constraint) and a
  partial index on it. Append-only, idempotent (column checked), existing rows stay NULL. `Txn.refundOfID`,
  `Txn.isLinkedRefund` (expense + `isRefund` + link).
- **Rules:** only an expense with `isRefund` carries a link; the original is an expense that is not a
  refund, not a balance correction, not a debt leg. Many refunds per expense; the sum of the linked
  refunds converted to the original's currency (at each refund's date) may not exceed the original
  amount (`RefundError.exceedsOriginal(remainingMinor:currency:)`). Transfers and corrections are never
  refunds. `TxnRepository.save` enforces the same on a row that carries a link (same currency always;
  another currency when the repository was given a converter, otherwise skipped).
- **Category:** a linked refund stores the original's category in its own `categoryID`. The store keeps
  it in sync (`RefundLinks.repair`, called by transaction save/delete, rule apply/rollback, import
  commit/undo and the debt conversions), so every calculator and SQL query keeps reading one column and
  nets that category without a join. A category merge (reassign) moves original and refund together.
- **Reporting:** a linked refund always reduces the original category's spending (a negative expense),
  on the refund's own day, in its own account currency converted at the refund's date like any amount,
  regardless of R-SET-3. Unlinked refunds follow R-SET-3. Changed: `Calc.reportEntries` (donut, budget,
  events, income vs expenses and list totals all go through it), `SQLiteReportQueries.spending`
  (`FlowRow.isLinkedRefund`), `TxnTotals`, `TxnRepository.summary` (grouped by the link flag),
  `TxnListSummary.Main.isLinkedRefund`, `TransactionTotalsRule`. Net worth and balances do not look at
  the link (cash moves anyway).
- **Deleting the original** clears the link of its refunds (they keep their own category, become
  unlinked expense refunds and follow R-SET-3 again). Same repair when the original becomes a transfer,
  a debt leg or a refund.
- **Repository:** `RefundRepository` (AbacusDomain/Protocols/RefundRepository.swift) and
  `SQLiteRefundRepository` (AbacusStore): `linkRefund(_:to:)`, `unlinkRefund(_:)`,
  `refundCandidates(for:matching:limit:)` and `refundCandidates(probe:matching:limit:)` (probe = a refund
  that is not saved yet), `refundTargets(for:matching:limit:)`, `refundLinks(for:)` (two aggregate reads
  per list page, indexed lookups, no per-row query). Convenience overloads without `matching:`.
- **List:** `TransactionsViewModel` takes `refunds:`; `Row.refundNote` ("Refunded zł 450.00", "Partly
  refunded zł 120.00 of zł 450.00", "Refund of Booking.com · 12 Oct"), `Row.refundJumpID`,
  `Row.isLinkedRefund`; menu rules `canLinkRefund`, `canChooseOriginal`, `canUnlinkRefund`; sheet model
  `RefundPickerModel` (`beginLinkRefund`, `beginChooseOriginal`, `chooseRefundOption`, `unlinkRefund`).
  App: context menu "Link a Refund…", "This Is a Refund of…", "Unlink Refund"; `RefundPickerSheet`;
  the note is a button that selects and scrolls to the other transaction when it is among the loaded
  rows, else opens it in the editor.
- **Editor:** "Refund of" row under the refund checkbox (None / "Booking.com · 2 Mar 2026", Choose…/
  Change…/Remove); picking takes the original's category; the link is saved with the transaction; a
  refund above the remainder is refused with "…Up to <amount> can still be refunded." Duplicate does not
  copy the link.

## Interpretations (owner to confirm)
- **"This is a refund of…" on an income row** turns it into an expense with `isRefund` (type `.expense`,
  money still comes in, balances unchanged), category = the original's, link set. Unlinking later keeps
  it an expense refund (it is not turned back into income). An income reversal (`income` + `isRefund`)
  and pending-at-bank rows are not offered.
- **Candidate lists:** expense candidates (for a refund) exclude refunds, corrections, debt legs and
  fully refunded expenses, and (same currency) those smaller than the refund; ranking: same description
  40 (contains 20), same currency 10 + same amount as the remainder 30 (else 5), same account 3; window
  60 days before the refund and not after it; a non-empty search drops the window and filters by
  description/note. Incoming candidates (for an expense): same account, amount not above the remainder,
  unlinked income or expense refund, ranked by equal amount 30, description match, date not before the
  expense.
- **Cross-currency cap** is checked in the original's currency at the refund's date rate; a refund that
  is the full amount can be refused by a few minor units when the rate moved between purchase and refund
  (the error says what remains). Without a known rate the link is refused (`rateUnavailable`); saving an
  edit of an already linked refund never fails for missing rates.
- **Linked refund's category is the original's** and follows it (also when the original changes); the
  editor does not let the user keep a different one (it is re-synced on save).
- **Jump:** the note selects and scrolls to the other row when it is on a loaded page; otherwise it opens
  that transaction in the editor (the list is paged at 500 and filtered).
- **List note shows the first refund** as jump target when several refunds exist.

## Proposed requirement and decision text (for the orchestrator)
- `R-TX-4` addendum: "A refund may be linked to the expense it returns (`refundOfID`). A linked refund
  always reduces that expense's category spending on the refund's own date, independent of `R-SET-3`;
  unlinked refunds follow `R-SET-3`. Many refunds may link to one expense; together (converted to the
  expense's currency at each refund's date) they may not exceed it. Deleting the expense unlinks them."
- Decision: "Refund links (C30): `txns.refundOfID` (v15), no FK; the linked refund keeps the original's
  category in its own column (repaired on every write path), so reports need no join."

## Import suggestion proposal for C31 (not built here)
At the preview step, for each incoming row that is a refund candidate (an expense row marked refund, or
an income row), call `RefundRepository.refundCandidates(probe: RefundProbe(accountID:, amountMinor:,
payee:, occurredAt:), matching: "", limit: 3)` with the row's account, its amount in the account
currency, its description and date (no id: the row is not saved yet). Offer the first candidate as a
suggestion only when `isSameAmount` and its `score` is at least 70 (same description + same amount);
show "Refund of <payee> · <date>" with an accept/ignore choice, default undecided like the other review
rows. Accepting stores the original's id on the row; after the batch commits, call
`linkRefund(newTxnID, to: originalID)` (it converts an income into an expense refund and takes the
original's category, and re-validates the cap). Rows imported in the same batch cannot be originals
until committed, so do the pass after the commit for those. The candidate query is read-only and cheap
(one indexed expense scan plus the linked-refund list), so it can run once per suggested row.
