# C15 — Rules: "Description starts with" and "Description equals" (R-IMP-8, D44)
State: done (waiting for merge)   ·   Branch: wp/C15-rule-match   ·   Updated: 2026-10-30

## Done
- **What `exactly` meant**: already whole-description equality — `RuleMatcher.conditionsHold`
  compared the folded description with the folded pattern (`text == pattern`). Only its label
  changes: the editor picker said "Description exactly matches", the rule row "Description is
  exactly “…”"; both now say **"Description equals"**. Raw value `exactly` is kept (stored in
  `categoryRules.matchKind`).
- **New kind `startsWith`** (`RuleMatchKind`, raw value `startsWith`): the folded description
  begins with the folded pattern (`hasPrefix`, a plain prefix, not a whole-word one: "uber"
  matches "Uber Trip" and "Ubereats"). Same normalisation as contains/equals
  (`RulePattern.normalized`: case, diacritics, whitespace runs collapsed and trimmed).
- **No migration**: `matchKind` is plain `TEXT NOT NULL … DEFAULT 'contains'` with no CHECK, so
  the new raw value stores as is. Note: an older build reading a `startsWith` rule would fail to
  decode it (single user, no downgrade path in use).
- **Editor**: `RuleFirstCondition.descriptionStartsWith`; picker order Contains / Starts with /
  Equals (`RuleFirstCondition.descriptionChoices`), mapping via `RuleFirstCondition(matchKind)`
  and `.matchKind`. Row text: "Description starts with “…”" / "Description equals “…”".
- **Ordering**: there is no specificity ordering; rules run in the user's order
  (`position`, then hit count, then pattern) and the first match wins. Kept as is — a kind-based
  priority would override the order the user set. Test `kindsDoNotReorder` pins it.
- **Import**: learned rules ("Will be saved as a rule …") stay `contains`; nothing to change.
- **Contract change**: `RuleMatchKind` in `AbacusDomain/Model/Entities.swift` gained a case
  (additive; every switch over it updated).
