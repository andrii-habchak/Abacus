# C47 — Text encoding: U+FFFD in rule text
State: done (awaiting merge)   ·   Branch: wp/C47-text-encoding   ·   Updated: 2026-11-01

## Diagnosis
- Every PKO export on this Mac (business PLN/USD, private PLN/EUR/USD, samples/private) is **pure Windows-1250**:
  no UTF-8 lines, no literal EF BF BD, no bytes Windows-1250 leaves undefined. In the business PLN file the
  ZUS recipient name uses single bytes A3 (Ł), D1 (Ń), A3 (Ł).
- `PKOText.decode` + `PKOParser` read that file correctly (checked by parsing it: no U+FFFD in any payee/note).
  So the app's PKO import does **not** produce the U+FFFD.
- The stored pattern "ZAK?AD UBEZPIECZE? SPO?ECZNYCH" has exactly the shape of those bytes read as *lossy
  UTF-8* (A3 -> FFFD, "D1 20" -> one FFFD, A3 -> FFFD); a test pins that shape. Text with that shape therefore
  came from some other reader of the same bank text (most likely a Saldo-side copy of the bank data, which
  the owner copied from) — not from PKO files in this repo. Not verifiable without the owner's database
  (not touched). Open question for the owner: where the description was copied from.

## Done
- `PKOText.decode` hardened: UTF-8 strict, else Windows-1250, else (mixed file / undefined byte) per line:
  a UTF-8-valid line as UTF-8, other lines as Windows-1250, an undefined byte -> U+FFFD for that byte only.
- Rules list + condition text show U+FFFD as the placeholder ▯ (`TextFolding.displayText`); stored text unchanged.
- Edit rule popup: help line (orange) when the pattern holds U+FFFD: unreadable characters, each matches any one
  character, retype to replace.
- `TextFolding.repairedPattern(_:in:mode:)`: the readable text an old pattern stands for, from a properly
  decoded text (tested). Basis for a repair.

## Not done
- No automatic/offered rewrite of stored rules during import (needs an import-time hook and owner decision on UI);
  the helper is ready. Workaround: retype the text in the Edit rule popup.
- Running app not inspected visually (builds and tests only).
