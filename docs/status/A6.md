## Done
- **Entry point** `AbacusImport/Pipeline/ImportPipeline.swift` (repository protocols only):
  `detect(_:)`, `statementCurrency(_:)`, `rememberedTargetAccount(for:)`,
  `preview(data:fileName:targetAccountID:)` (alias `pkoAccountID:`), `remapAccount(_:key:to:)`
  (async: dedupe depends on the account mapping), `commit(_:) → ImportSummary`, `undo(_:)`,
  `history()`.
- **Preview model** `ImportPreview` (value type for B6's view model): `rows: [PreviewRow]` with
  status / detail / type / account refs / amounts / category + `categorySource` / `rulePattern` /
  `duplicate` (existing txn + action) / `review` (reason, pair candidates, suggested, choice) /
  `eventTag`; `counts` per status (new, already imported, possible duplicate, settles pending,
  needs review, skipped incl. parser-skipped), `accountMappings`, `categoryMappings`,
  `eventCandidates`, `rulesToSave`, `uncategorisedCount`, `unresolvedReviewCount`, `issues`,
  `transactionsToCreate`, `canCommit`, `dateRange`, `fileWarnings`. Mutations: `setCategory`,
  `resetCategory`, `setSavesRule`, `setDuplicateAction`, `setReviewChoice` (pairing is mutual),
  `acceptSuggestedReviewChoices`, `setEvent`, `mapCategory`, `acceptDefaults`/`acceptingDefaults`.
- **Mapping** (R-IMP-2): remembered mapping → same name + currency (accounts) / name + kind
  (categories) → create (kind from Saldo type, archived flag kept). PKO "Cash" → remembered →
  same name → the first non-archived cash account in the currency → create "Cash <CUR>". PKO
  target account remembered per statement currency (mapping key `statement|<CUR>`).
- **Rows → transactions**: expense/income/refund, transfers (+ fee and refund lines, D22),
  original amounts, opening balances only for accounts the import creates (else `skipped`),
  PKO own-account transfers by normalised account number (`AccountNumber.normalized`), PKO
  currency exchange halves as transfers when the other account's number is known.
- **Dedupe** (`Dedupe/`): exact by fingerprint; fuzzy possible duplicate (default skip,
  import anyway, link); pending hold → settled upgrade; one existing transaction per row.
- **Needs review**: unpaired halves (pair with a half of the file, pair with an existing expense,
  transfer to an account, record as expense/income with a category, skip), unknown PKO types,
  own-account transfers with unknown received amount. Commit refused until each has a choice.
- **Rules** (`Rules/`): `RuleMatcher` (first match in repository order, case-insensitive
  contains, optional account, category kind must match; usable by the editor, R-EDIT-3) and
  learning: a category picked for a row the file and rules left empty → pattern
  `RulePattern.derive` (first ≤ 3 words without digits) → applied at once to the file's other
  uncategorised rows, saved on commit (`origin .imported`); applied rules get hit counts.
- **Commit**: one `ImportCommit` (batch with summary line, accounts, categories, events,
  txns + lines, fingerprints, upgraded/converted txns, mappings, rules) → `ImportSummary`
  (counts + `lines` for the done screen).
- **Tests** (all named with requirement IDs): `PipelineTests`, `DedupeTests`, `RulesTests`,
  `PipelineDefaultsTests` on fakes; `PipelineIntegrationTests` on the in-memory SQLite store;
  `PipelineRealDataTests` (`.realData`).
- **Real exports** (headless defaults path, in-memory store): Saldo 3 923 rows → 3 888
  transactions (964 paired transfers, 280 review halves recorded), 43 accounts, 33 categories,
  preview + commit 0.74 s; all 24 account balances equal the Saldo legs; re-import 0 new. PKO
  79 rows → 79 transactions, balance = latest booked "Saldo po transakcji" minus open holds;
  re-import 0 new. The statement had 0 possible duplicates against each of the 4 Saldo PLN
  accounts (Saldo does not cover it).

## Headless defaults (`ImportPreview.acceptDefaults()`)
For the command-line import before B6 exists: `preview(data:fileName:pkoAccountID:)` →
`acceptingDefaults()` → `commit(_:)`.
- account and category mappings as proposed; new ones are created;
- possible duplicates skipped; pending holds upgraded (automatic anyway);
- no Saldo tag becomes an event (even one named like an existing event);
- unpaired transfer half → expense (outgoing) / income (incoming) in category "Uncategorised"
  of that kind (existing one by name, else created), note "Unpaired transfer half — review";
- unknown PKO types and own-account transfers with an unknown amount → expense/income by sign,
  no category;
- choices already made are kept.

## Interpretations (for the orchestrator to confirm or move to DECISIONS)
1. Fuzzy dedupe (R-IMP-4): the "similar description" condition is waived when the dates are the
   same day or the existing transaction is a transfer (Saldo "ATM" vs PKO "BANKOMAT …"); a missed
   duplicate double-counts silently, a flagged one is visible. Similar = one text contains the
   other, or a shared word ≥ 4 chars (diacritics/case folded), or one such word prefixes another.
   Candidates from the same source are never flagged (exact fingerprints handle those).
2. Each existing transaction matches at most one row (closest date first): two identical PKO
   rows against one Saldo transaction → one possible duplicate, one new.
3. PKO own-account transfer whose other side was imported from the other account's PKO
   statement: an existing transfer between the two accounts is linked automatically (status
   "already imported"); an existing PKO expense/income on the other account is converted into
   the transfer (an `updatedTxns` change; R-IMP-PKO-3 "paired with the other side"). Other-source
   matches go through the fuzzy rule instead.
4. Pairing a half with an existing transaction is offered only for incoming halves (the existing
   expense keeps its account and attached records); outgoing ones would move the existing
   income's records to another account.
5. A new account's opening date is the start of the first day the file touches it; its opening
   balance is the sum of the file's opening rows. Existing accounts' opening rows → `skipped`.
6. Event candidates are unticked by default unless an event with the same name exists; events are
   created only when a new transaction uses them.
7. Learned rules are global (no account); a pick on a row categorised by the file or a rule saves
   no rule. Settled upgrades keep the hold's description and take the settled original amount.
8. `Txn.bookedDay` is set only when it differs from the purchase day.
9. Recording a half "against" its direction keeps the balance: income for money out is an income
   reversal, expense for money in a refund (`isRefund`).
