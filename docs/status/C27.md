# C27 Multi-select drag and drop, drag scrolling — status

_Branch `wp/C27-list-multiselect`. Builds on S2 (D55), D48, R-MGMT-8/9. Lane C26 owns the account
editor sheet/draft; this lane did not touch it._

## Done

- **Multi-selection (Accounts and Categories).** The outline now has `allowsMultipleSelection`,
  so the click rules are the native Finder ones: plain click = one row; Cmd+click toggles only the
  clicked row; Shift+click selects from the anchor (last clicked row) to the clicked row **in
  visible order**. Rows hidden inside a collapsed group are not visible, so they are not selected
  by a range; a selected group is dragged together with its children anyway (below).
  - Models: `selection` stays the single selected row (inspector, "New transaction on the selected
    account", sheets). New `multiSelection` / `selectedIDs` and `select(ids:)`: one id behaves as
    before; two or more clear `selection` and the drafts. A reload keeps the rows that still exist.
  - **Edit with several rows selected:** double-click and context menu "Edit…" apply to the
    clicked row only (the sheet opens for it); Return does nothing while several rows are
    selected (ambiguous). Right-click on a selected row keeps the selection.
- **Multi-row drag.** Dragging any selected row drags the whole selection (list order). The list
  hands `OutlineDrop.moving: [UUID]` to the models, `canDrop(_ [UUID], …)` / `drop(_ [UUID], …)`
  (the single-id API stays and calls them).
  - `draggedItems(_:)`: a selected group (accounts) / parent (categories) carries its own
    children, so selected children of a selected parent are left out: nothing is moved twice and
    the hierarchy is not broken. Unknown ids and the built-in Uncategorised row are dropped.
  - Same rules for every item, applied one by one in list order (after a row: last item first, so
    they land in list order): reorder between rows, nest onto a category, onto a group / an
    account in a group, group creation.
  - **Refusal is all or nothing:** if any dragged item can't go there (a group or a parent with
    subcategories onto a row, a row onto itself or onto/next to another dragged row,
    Uncategorised in the selection, a group into its own account) the proposal gets the no-drop
    cursor and `drop` changes nothing. Accounts already in the target group are skipped as long
    as one really moves.
  - Accounts onto an ungrouped account: one name prompt, one group holding the target (first)
    and every dragged account (`AccountGroupPrompt.alsoMoving` / `allMoving`, additive).
  - Dropping next to a dragged row itself is refused (Finder does the same).
- **Drag scrolling (`DragScroller` in `OutlineList.swift`, `OutlineAutoScroll` in
  `AbacusFeatures/Manage/OutlineDropResolver.swift`).** Investigation: the outline is already an
  `NSOutlineView` in an `NSScrollView` (not a SwiftUI `List`), so the right layer is the outline.
  Once a drag session starts AppKit runs its own tracking loop, which swallows scroll-wheel
  events; the outline's built-in edge autoscroll is not something we control. Fix, active only
  while a drag from this list is in flight: a local scroll-wheel monitor scrolls the list under the
  pointer (and consumes the event), and a 60 Hz timer (common run-loop modes) scrolls while the
  pointer is within 36 pt of the top/bottom edge, speed growing towards (and beyond) the edge.
  If the outline scrolls by itself (clip origin changes that we did not cause) the timer steps
  aside so speeds do not add up. Both are removed when the session ends or the view is torn down.

## Verified

- `swift test` (with `ABACUS_SAMPLES`) green; new suite `MultiSelectDragTests` (14 tests):
  selection set for both pages, `draggedItems`, reorder before/after, onto group (skip members),
  multi group creation, refusals (nothing changes), group moved with its own accounts (no
  duplicates, hierarchy intact), single-item regression for both pages, edge-scroll step.
- App build green.
- **Not verified in the running app.** The terminal has no Accessibility permission (as in S2), so
  no real mouse drag, Cmd/Shift click or wheel-during-drag could be driven. The model rules and
  the edge-scroll step are unit-tested; the AppKit wiring (multi-row `NSOutlineView` drag, the
  scroll-wheel monitor, the edge timer) is compiled but untested by a pointer. Owner try-out:
  Cmd/Shift click then drag several rows; during a drag use the wheel/trackpad and hold the
  pointer at the list's top/bottom edge. If the wheel still does nothing during a drag, the local
  event monitor is not receiving scroll events from the drag loop and a different hook is needed.
