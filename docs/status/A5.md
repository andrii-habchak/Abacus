# A5 — Store
State: done   ·   Branch: wp/A5-store   ·   Updated: 2026-10-21

## Done
- `AbacusStore/Repositories/`, one file per type, all over the database from
  `AbacusDatabase.open(at:)`:
  - `SQLiteAccountRepository` — list/save/archive/delete; R-ACC-1 currency locked after the first
    transaction (`StoreError.currencyLocked`); R-ACC-5 delete only without transactions on either
    side of a transfer; `balances(asOf:)` (R-ACC-3).
  - `SQLiteCategoryRepository` — R-CAT-2 one level, same kind (`StoreError.invalidParent`,
    `kindMismatch`); archiving a parent archives children; R-CAT-3 delete: in use = transactions,
    attached records or budget allocations; reassignment moves those plus rules and import
    mappings (allocations merged into the target's); children move up first.
  - `SQLiteTxnRepository` — save replaces attached records, delete cascades; list query with every
    `TxnQuery` filter (calendar-day bounds in the user's time zone, parent → children,
    attached-record categories, either transfer side, type, event), Unicode case-insensitive
    search on payee, note and attached-record notes, sort; `list(matching:)` adds `TxnTotals`
    (per currency and day, so each bucket converts at its date's rate; with a category filter only
    matching parts count).
  - `SQLiteReportQueries` — `monthlySpending` / `spending(from:to:eventID:)`
    (`SpendingReport`: expenses, income, refunds by category/currency/day, attached records
    included, refunds per R-SET-3, refund lines per D22), `totalsByCategory`,
    `rolledUpToParents`; `balances(on:)` / `netWorthSeries` (`BalanceSeries.netWorth`, month-end
    at that day's rate, last point at the latest rate, archived accounts excluded).
  - `SQLiteBudgetRepository` (R-BUD-1/3), `SQLiteEventRepository` (+ `activeEvents(on:)`),
    `SQLiteRuleRepository`, `SQLiteSettingsRepository` (typed helpers with defaults),
    `SQLiteRateStore` (upsert by id and by (day, base, quote, provider); whole cache in one query;
    latest day per pair; overrides).
  - `SQLiteImportStore` — fingerprint lookups (chunked), dedupe candidates, pending holds,
    mappings; commit in one transaction (inserts only, so existing rows and opening balances can't
    be overwritten; only `updatedTxns` change existing transactions; mappings replace by key);
    undo by batch; `transactionCounts()` for the history.
  - `SQLiteBackup` — export = SQLite backup to one file; restore validates, migrates a temporary
    copy (old backups gain new columns, e.g. `bookedDay`), then replaces all tables in one
    transaction via ATTACH (observers and future sync triggers see the changes).
- `Txn.bookedDay` (schema v2) carried by every path (whole-row reads/writes); tests cover save,
  import, settled upgrade, backup and a v1 backup.
- Tests: 59 in `AbacusStoreTests`, names carry the requirement IDs (R-ACC-1/3/4/5, R-CAT-2/3,
  R-TX-4/6, R-LIST-1…6, R-BUD-1/2/3, R-EVT-1/2/3, R-FX-1/2, R-IMP-2/3/4/6/7/8, R-IMP-PKO-2/4,
  R-SET-1/2/3, R-HOME-1/3, R-NF-2). Full `swift test` green; app builds.
- Performance (R-NF-2), 20 000 synthetic transactions: committed in one import well under 10 s;
  six list queries with totals and two dashboard aggregations. Optimised build (`swift test -c
  release`): slowest list query (5 000 rows) 78 ms; unoptimised ~180 ms, so the debug test budget
  is 400 ms (200 ms in release builds).

## Blockers / contract-change requests (for the orchestrator)
1. Optional: `RepositoryError` could absorb `StoreError.currencyLocked` / `.invalidParent` so
   callers only see the shared error type. Stubbed as `AbacusStore.StoreError` meanwhile.
2. Optional: `TxnRepository` has no totals or single-fetch method; the concrete type offers
   `list(matching:)` and `transaction(_:)`. Add them to the protocol if view models should depend
   on the protocol only.
3. Undo of an import cannot restore fields of upgraded/linked transactions (`updatedTxns`) nor
   remove accounts/categories/events the batch created — no table records the previous state or
   the batch's created entities. If wanted: a snapshot table (or `importBatchID` on
   accounts/categories/events) in a later migration.
