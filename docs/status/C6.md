# C6 — Budget limits in their own currencies (D43)

Branch `wp/C6-budget-currency`. TA v1.5 `R-BUD-1/2`, `R-HOME-2`, `R-MGMT-3`; decisions D27, D30,
D43.

## State: done

### Model and migration

- `BudgetAllocation.currency` (NOT NULL). `BudgetAllocation.limit` gives the limit as `Money`.
- `BudgetPlan` keeps its `totalMinor` / `currency` columns (migrations are append-only and
  CloudKit-safe), mapped in Swift as `legacyTotalMinor` / `legacyCurrency` so nothing reads them
  by mistake. New plans write 0 and the first limit's currency.
- Migration `"v5: budget allocation currency"` (registered after the others; C5's `"v4: colours"`
  goes before it):
  1. `ALTER TABLE budgetAllocations ADD COLUMN currency TEXT NOT NULL ON CONFLICT REPLACE DEFAULT 'PLN'`
     (the default only matters for rows written without the column, e.g. older-schema records);
  2. `UPDATE budgetAllocations SET currency = (plan's currency)` for every allocation whose plan
     exists (all of them: `planID` is NOT NULL with ON DELETE CASCADE).
  Nothing is dropped or rewritten except the new column, so the owner's budget keeps every limit
  and amount, each in its plan's old currency.
- Backup/restore copies columns generically after migrating the backup, so nothing changed there;
  a pre-v5 backup restores with each limit in its plan's currency (tested).

### Calculator (`AbacusDomain/Calc/Budget.swift`)

- `BudgetLine` is in its allocation's currency: spent = the month's expense entries of the
  category (children too unless they have their own limit, D27) converted at each entry's day
  rate. Status ok/near/over is decided in that currency, so the display currency never changes
  it.
- `BudgetStatus` has the sums in a given currency (`currency:` parameter = the display currency),
  at `budgetTotalRate`: the latest rate for the current (or a future) month, the month's last day
  for a closed one (D30). `status` of the total is computed from those sums.
- Missing rates are never converted at 1: spending without a rate to its limit's currency goes
  into `unconverted`; a line without a rate to the display currency is left out of both sums and
  recorded in `totalUnconverted`.

### Interpretations

- **Total spent = spending in categories that have a limit.** With no "unallocated" row, spending
  in other categories (bills, fees, uncategorized) is not part of the budget total; it still shows
  in the expenses donut.
- **Category bars are shown in each limit's own currency** (e.g. "€27.83 / €110.00"): those are the
  amounts the owner typed, and the status is decided in that currency. Only the headline total is
  converted. A note under the total says "Limits in PLN, EUR · total in UAH at the latest rate"
  (or "at the rate of <month end>"), or names the currencies without a rate.
- **Total status** (the big bar's colour) comes from the converted sums, so it can move slightly
  with the display currency; category statuses cannot.
- **Editor**: no total field; each row has a currency picker. A new limit starts in the last
  currency used (picked, or the last loaded row), else the display currency (read from settings).
  The Share column stays: each limit's share of the total in the display currency at the latest
  rate. A footer row "Total in <display currency>" shows the sum (limits without a rate are left
  out and named in red). The editor re-reads the rates when they change (`refreshRates`, called
  from `AppSession.ratesChanged`), keeping unsaved edits.
- **Two limits of one category** (not written by the app): the calculator adds them in the first
  one's currency at the total's rate.
- **Category delete with reassign**: limits in the same currency add up as before; in different
  currencies the target keeps its own limit and the moved one is dropped (the store has no
  converter). Same in `ManagePreviewStore`.
