# C28 — Transactions list performance and filters
State: done (awaiting merge)   ·   Branch: wp/C28-list-filters   ·   Updated: 2026-10-30

Owner-approved after testing 1.4.1: (1) fix the slow "All dates" list at the root (fixed rows, paging,
whole-set totals, date range restore), (2) cascading filters, (3) a single row of dropdown buttons, no
chips. Owned: `AbacusFeatures/Transactions/` (list + filters), `App/macOS/Transactions/` (not the
convert-to-debt sheet), the list query code in `AbacusStore/Repositories/TxnRepository.swift`.

## 1. Cause analysis (performance)

- C24 found that AppKit sizes every inserted row of the `List` (an `NSTableView`) on the main thread;
  keying the list by the loaded query made a filter change rebuild instead of diff, but the table still
  received *all* rows (about 5,000 rows with nested lines, each a SwiftUI view with an automatic height).
  Opening "All dates" = thousands of rows built and measured; dragging the scroller makes AppKit ask for
  the height of rows far from the viewport (estimated heights get replaced by real ones as they come
  into view) so the thumb lags while wheel scrolling (small steps) is fine.
- The model side was also O(all rows): fetch every `Txn` and its lines, format every row (date and money
  formatters), compute totals and day nets row by row. Load also read every uncategorised transaction of
  the whole history only to know whether to show "Uncategorised".

## 2. Design

- **Fixed heights**: row 40 pt, nested line 18 pt, day header 30 pt (`TxnMetrics`), set with exact
  `.frame(height:)`; nothing is measured from content.
- **Paging** (`TransactionsViewModel`): `pageSize` 500. `reload()` fetches the first page (or, for an
  unchanged query, as many rows as are already loaded, so an edit keeps scroll position and selection)
  and the **aggregate of the whole filtered set**. `loadMore()` appends the next page when the row 100
  before the end appears (`rowAppeared`); the new rows join the last day section when they share its day
  (a page boundary may fall inside a day); the list keeps its identity (`loadedQuery`, C24), so there is
  no rebuild and no jump.
- **Whole-set numbers**: `TxnRepository.summary(matching:)` returns the row count and the amounts
  grouped in SQL by minute / account / type / refund flag / category (and attached records likewise).
  The Features layer applies the existing `TransactionTotalsRule` to those groups and converts each
  (day, currency) bucket at that day's rate (`TransactionListContent.Builder`). The footer, "N
  transactions" and every day header's net therefore do not depend on which pages are loaded. A minute
  never straddles two local days (UTC offsets are whole minutes), so grouping by minute is exact; the
  local day is taken in Swift with the repository's calendar.
- **Selection**: stays a single row id (the list has no bulk actions); it is cleared only when its row
  is not in the reloaded rows. Select-all of the list control would only cover loaded rows (there is no
  bulk action that uses it).
- **Date range restore**: `TransactionFilters.dateRangeBeforeDebt` is set by `filters(showingDebt:)`
  ("Show transactions" of a debt uses all dates); removing the last debt puts the range back unless the
  range was changed by hand meanwhile (a `didSet` on `dateRange` forgets it). "Clear filters" returns to
  the default (last 30 days). The date menu has an explicit "All dates" item now.
- **Cascading filters**: `TxnRepository.facets(matching:dimension:)` = four GROUP BY queries (accounts incl.
  both sides of transfers, categories incl. attached records, events, types), each computed under the
  query with that menu's own filter dropped. Debts are derived from the accounts facet (a debt is offered
  when one of its accounts has rows). Menus list only values with rows plus the selected ones; a selected
  value with no rows stays visible with an orange "no rows" mark and is never auto-cleared. Counts are
  shown where they are exact (accounts, events, types, leaf categories). The C24 rule (a selected debt
  limits Accounts to its accounts) is kept. Facets are recomputed at the end of every `reload()`, a newer
  call supersedes an older one and a cancelled task stops at once (the view's `.task(id: query)` already
  debounces typing by 150 ms).
- **Interpretation, "Uncategorised" with a debt**: a debt's rows are transfers, which have no category and
  never matched "Uncategorised" (R-HOME-3 slice = expenses/incomes without category). While a debt is
  filtered the query sets `uncategorisedIncludesTransfers`, so Uncategorised is offered (and matches) for
  them, as the owner asked; without a debt filter nothing changes.
- **Filter bar**: no chips at all (debt chip, account chips and the import chip are gone; the import filter
  is a button with a menu item that removes it). One row of buttons: Date, Categories, Accounts, Debts,
  Types (was a segmented control; now a menu with counts), Event, [Import], then Clear filters and sort.
  Same blue outline on every filtering button. Below 1,120 pt width the labels are shortened and the row
  scrolls sideways; it never wraps.

## 3. Measurements

Real app, debug build, scratch database (`-AbacusLoadLargeSampleData YES -AbacusLargeSampleTransactions <n>`,
DEBUG probe `-AbacusTransactionsAllDates YES -AbacusHangWatch YES`: switches to All dates, jumps the
scroller, changes a filter; "responsive" = wall time until the main thread answers promptly again). An
optimised build gave the same numbers (the cost is inside SwiftUI/AppKit, not in our code).

| Step | before 5,000 | after 5,000 | before 20,000 | after 20,000 |
|---|---|---|---|---|
| All dates: first rows responsive | 1,190 ms | 314 ms | 3,566 ms | 463 ms |
| Scroller jump to 50 % | 692 ms | 53 ms | 2,415 ms | 50 ms |
| Scroller jump to 95 % | 1,321 ms | 62 ms (+ next page) | 4,669 ms | 65 ms |
| Filter change (expense only) | 1,057 ms | 318 ms | 3,095 ms | 429 ms |
| Append of one more page (500 rows) | n/a | about 60 ms at any size | n/a | about 60 ms at any size |

Model side only (`TransactionsListBenchmarkTests`, debug, includes summary and facets): first rows 191 -> 71 ms
(5,000), 726 -> 199 ms (20,000); next page 17 ms.

Found on the way: (1) a nested `ForEach` (days > rows > lines) made every appended page cost about 0.5 ms per
already-loaded row in SwiftUI's list diff (2.2 s at 4,500 rows); one flat `ForEach` over
`TransactionListContent.items` (header / row / line) removed it. Day headers are plain rows now, so they no
longer float over the rows while scrolling. (2) A single trigger row for the next page can be skipped when
the scroller jumps, so the last 100 loaded rows all trigger it.
