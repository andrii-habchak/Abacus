## Done

### 1. Column sorting of the review rows
- Every column header of the row list (Status, Date, Description, Account, Amount, Category / action) is a
  button: first click ascending, second descending, third back to the file's order (the default). The
  sorted column shows a chevron (up = ascending); the others stay grey. Tooltips say what the next click does.
- Applies to the Transactions tab and to the "Rows that need a category" list in Needs review (same header).
  The decision cards are not sorted.
- Keys: Status = the status order of `RowStatus` (New, Already imported, Possible duplicate, Settle pending,
  Needs review, Skipped); Date = the transaction's day; Amount = signed (money out negative, so ascending
  starts with the largest payment out); Description / Account / Category / action = text, Finder order
  (case- and diacritic-insensitive). Category / action uses the picked category, else the debt line, the
  duplicate action or the note; rows still without a category sort first. Equal keys keep the file's order.
- The sort is kept while the file is reviewed and for the next file (it is a view preference).
- Selection: the selected rows stay selected across a sort; Shift+click ranges over the visible (sorted)
  order, Select all takes the visible rows, as before.
- Code: `AbacusFeatures/Import/ImportSorting.swift` (new: `ImportSortColumn`, `ImportRowSort`,
  `toggleSort`, `sortDirection`, `sorted`), `ImportWizardModel.rowSort` / `visibleRows`,
  `ImportBulk.visibleCategoryRows`; header in `App/macOS/Import/ImportRowsTab.swift` (`ImportRowsHeader`
  now takes the model), one call in `ImportOtherTabs.swift`.

### 2. "Undo of PKO_business_USD.csv did nothing" — bug found and fixed
- **Root cause (UI, every undo).** The confirmation dialog's "Undo Import" button ran
  `Task { await model.confirmUndo() }`. When a dialog button is pressed SwiftUI also closes the dialog, which
  sets the `isPresented` binding to false → `model.cancelUndo()` → `pendingUndo = nil`. The task runs after
  that (it is queued on the main actor), finds `pendingUndo == nil` and returns without doing anything, no
  error. The same applied to "Undo this import" on the Done step. The model tests called `confirmUndo()`
  directly, so they never saw it. (Found by reading the code; the race does not depend on the order in which
  SwiftUI calls the action and the dismissal. Not reproduced by clicking in the running app.)
- **Fix.** `ImportWizardModel.startConfirmedUndo()` takes the batch synchronously and starts the undo with
  it (`confirmUndo(_ batch:)`); the button calls it. Test `undoSurvivesDialogDismissal` replays the
  dialog's order (action, then `cancelUndo`).
- **Feedback.** After an undo an alert "Import undone" says what happened: "… was undone: N transactions
  removed", or, for a batch without transactions of its own (all rows were already imported, skipped or
  linked to existing ones), that it is only marked undone and nothing of its own was removed. The
  confirmation message says the same up front with the count. The History panel shows per batch
  "N transactions from this import" or "No transactions of its own …".
  Counts: `ImportWizardDependencies.batchTransactionCounts` (live: `SQLiteImportStore.transactionCounts()`),
  `ImportWizardModel.batchCounts`, `undoNotice`.
- **Undo while the same file is open in review.** If the undone batch went into the file's "Import into"
  account (or an account where the file's rows were found), the review is built again, so rows that showed
  "Already imported" become New and can be imported (into another account too). Review choices made so far
  are dropped, as with any change of "Import into" (`reviewAfterUndo(of:)`).
- **Known, not fixed** (STATUS open item, `docs/status/C38.md`): when a later import absorbed a
  transaction (turned an income/expense into one side of a transfer), the transaction keeps the batch id of
  the import that first created it. Undoing that *earlier* batch deletes it — the whole transfer goes,
  with the later import's side. Undoing the later (absorbing) batch first restores it. A fix needs a rule
  on what survives (re-tag the transfer to the absorbing batch, or turn it back into the later row); not
  trivial, left open.

### 3/5 (cheap part). PKO "Import into" checks
- **Imported elsewhere.** When the file's rows are already imported into another account than the one in

  “X”. Undo that import in History first, or they will be in both accounts." Found by recomputing the

  `ImportPipeline.alreadyImportedRows(of:in:)` (new file `AbacusImport/Pipeline/ImportTargetCheck.swift`),

  (`ImportWizardModel.targetWarning`, `targetOverlaps`, `AbacusFeatures/Import/ImportTarget.swift`.)
- Not changed: the default itself (still "last account used for this currency"); Import is not blocked.

## Answers

### 3. Why did PKO_business_USD.csv go to "PKO private $", and why could it not be changed?
- **How the default is chosen.** A PKO statement has no own-account field. On commit the pipeline remembers
  `statement|<currency>` → target account (`CommitBuilder.swift`, `remember(.account,
  ImportPipeline.statementKey(account.currency), target)`); on open `rememberedTargetAccount(for:)`
  (`ImportPipeline.swift`) reads the currency of the file's first row and returns the account the **last**
  statement in that currency went into. No file signature, no file name, no "first account with the
  currency". The owner's USD statements were set to go to "PKO private $" (STATUS, 2026-10-21), so every
  USD file — the business one too — defaults there. Only when nothing is remembered does the review ask
  (`ImportTargetPrompt`).
- **Why it could not be changed in the review.**
  - The bulk bar's **Account** action is not "move this row to account X". It makes a new expense/income a
    transfer to/from another own account (C31, `ImportPreview.setTransfer(toAccount:)` / `canTransfer`), so
    it is disabled for rows that create nothing — "Already imported" rows included. That is by design.
  - The whole-file control is **"Import into"** in the file bar. It is enabled for already-imported rows
    and rebuilds the preview for the chosen account; but it lists only **active accounts in the file's
    currency** (`targetOptions`). If the business USD account did not exist yet (or is archived, or has
    another currency), it is not offered — the account must be created first.
  - If it was offered and picked, the rows showed as New in the business account while the earlier import
    stayed in "PKO private $": importing would have put them in both. Before C41 nothing warned about
    that, and the Undo that should have removed the first import did nothing (bug 2).
- **Now (C41).** Flow that works: History → Undo import… (now works, says what it removed) → the open
  review rebuilds → choose the business account in "Import into" → Import. The warning line explains it
  when the rows are already in another account. Choosing the business account and importing then remembers
  USD → business account (see the proposal in 5 for the per-currency limit).
- **Proposal (not built):** a History action "Move to another account…" for a PKO batch that rewrites the
  batch's transactions' account and fingerprints in one transaction (same currency only; refused when a
  transaction of the batch is a transfer, refund link, debt record or settled hold). Cheaper than undo +
  re-import because category edits made after the import survive.
- Side note: `rememberedTargetAccount` also returns an **archived** account, which `targetOptions` does not
  list, so the picker would show no selection. Rare; left as is.

### 4. "Re-import the same file and edit it to rewrite the previous import" — concerns and a safe design
Concerns with letting a second import overwrite the first:
- **Fingerprints include the account** (PKO: `Fingerprint.pko(accountID:parts:)`; Saldo: the Saldo id).
  Re-importing into the same account finds every row "Already imported" and creates nothing; into another
  account it creates duplicates. A rewrite needs its own matching (old txn ↔ new row by fingerprint parts
  without the account), not the dedupe path.
- **Edits made after the import.** Categories, notes, payees, splits (attached records), events changed in
  Transactions would be lost or would conflict with the review's choices. Needs a per-field rule (keep
  user edits? overwrite?) and a diff the owner can see.
- **Links to other records.** Transfers paired with another account's side (C38 counterparts, absorbed
  transactions, estimates), refund links (`refundOfID`, C35), debt records/legs (C17/C22) and linked
  duplicates point at the old transaction ids. Rewriting must keep ids (update in place) or re-point every
  link; deleting and re-creating breaks them.
- **Pending holds.** A hold settled by the old import was upgraded in place (not tagged with the batch);
  a new file may contain the settled row or not — rewriting can re-open or double-settle.
- **Rules.** The first import learned rules and bumped hit counts; a rewrite with other choices learns
  conflicting rules unless it reconciles them.
- **History/undo.** Which batch owns a rewritten transaction? Undo of the second batch must restore the
  first import's state (snapshots like C38's `ImportTxnSnapshot` for every touched row), and undo of the
  first batch after a rewrite must not delete the rewritten rows unexpectedly.
- **Balances / FX.** Moving rows between accounts or changing transfer amounts changes balances, net worth
  history and converted totals; created "Balance correction" transactions may no longer fit.
- **Created entities.** Accounts/categories/events created by the first batch and remembered mappings
  (`statement|<currency>`, category mappings) must be reconciled.

Recommended design:
1. **Default: Undo + re-import** (what works now with C41): exact, simple, and undo already restores links
   it knows (C38 snapshots). Its cost: edits made after the import are lost — the confirmation should say
   so when the batch's transactions were edited (a future check: `updatedAt > importedAt`).
2. **If more is needed, an explicit "Re-import and replace" mode**, never implicit: started from the batch
   in History ("Replace with a new file…"), it opens the review with the old batch's rows matched to the new
   rows (fingerprint parts without the account), shows per row Unchanged / Changed / New / Gone, keeps
   transaction ids (update in place), keeps user edits by default, refuses or asks for rows with links
   (transfers, refunds, debts, settled holds), and is undoable as one step (snapshots of every changed
   transaction). The narrower "Move to another account…" action (answer 3) covers the owner's actual case
   with far less risk and should come first.

### 5. Why does PKO_business_PLN.csv default to "PKO private" (PLN)? Can the file identify its account?
- **Why:** same mechanism as 3: the remembered `statement|PLN` mapping points at "PKO private" (set when the
  personal PLN statement was imported), and the business file is also PLN.
- **What the file contains** (checked read-only, structure only): the same header as the personal export
  — `Data operacji, Data waluty, Typ transakcji, Kwota, Waluta, Saldo po transakcji, Opis transakcji` + 5
  unnamed detail columns (the USD business file has 6 unnamed columns, 13 in all). Windows-1250, one row
  per operation. **There is no own account number / IBAN anywhere** — not in a header block, not per row.
  Detail columns carry only the counterparty's account (`Rachunek odbiorcy` on outgoing rows, `Rachunek
  nadawcy` on incoming rows), names, titles, ZUS/tax form fields (`Nazwa i nr identyfikatora`, `Symbol
  formularza`, `Okres płatności`) and references. Business-only operation types appear
  (`Przelew do ZUS`, `Przelew podatkowy`, `Naliczenie odsetek`, `Obciążenie`, `Opłata za użytkowanie karty`;
  USD: `Przelew zagraniczny i walutowy`), but those are hints, not identifiers.
- **Mapping other than by a remembered default:**
  - *Fingerprint overlap* (implemented as a warning, C41): if the file's rows are already in an account,
    that account is the right one for overlapping statements. Could also *choose* the default when the
    remembered account has no overlap and exactly one other account has (proposed; not done because it
    only helps for overlapping periods).
  - *Running-balance continuity* (proposed): the oldest row's `Saldo po transakcji − Kwota` is the balance
    before the file; the candidate account whose stored balance on that day equals it is almost certainly
    the right one. Strong signal with no owner input, but needs the balance calculator in the import path
    and fails after manual corrections.
  - *Own-transfer IBANs* (weak): a counterparty IBAN equal to an Abacus account's IBAN tells which account
    the file is **not** from.
  - *File name* is the owner's own naming (`PKO_business_PLN.csv`), not the bank's, so it is not reliable;
    a remembered "file name pattern → account" would work only as long as the owner keeps naming files so.
- **Best UX (proposal):** remember per currency as today, but when more than one active account has the
  currency, *don't preselect silently*: preselect by balance continuity, else fingerprint overlap, else the
  remembered one, always with the yellow "check this account" line (done), and optionally require one click
  on "Import into" before Import is enabled when the choice is ambiguous and came from memory (not done —
  it adds a click to every monthly import of the personal account; owner to decide). Keep the target
  account's name visible in the Import button ("Import 18 transactions into PKO business").
