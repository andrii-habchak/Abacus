# A4 — PKO parser
State: done   ·   Branch: wp/A4-pko   ·   Updated: 2026-10-21

## Done
- `PKOParser: ImportParser` in `AbacusImport/PKO/`, created for the account the user picked
  (`init(account:)` or `init(accountID:currency:)`); every row has `account.resolvedID` set.
  - `PKOText`: Windows-1250 decoding (a file that is valid UTF-8 is read as UTF-8), CSV records
    with quotes, doubled quotes, CRLF/LF, line numbers. `canParse` checks the 7 named header
    fields.
  - `PKODetails`: `Key: value` columns 7–12 in any order; `Lokalizacja` → merchant (`Adres`);
    counterparty name/account; `Oryginalna kwota operacji` with or without a currency code.
  - `PKOTransactionType`: every type in the spec; unknown → kind by sign + row warning.
  - Kinds: card/BLIK payments → expense, positive → refund (R-TX-4); transfers and phone
    transfers → expense/income by sign; `Blokada` → expense, `isPending`, dated by value date;
    ATM withdrawal → `.transfer` to `PKOParser.cashAccount(currency:)` (external account
    "Cash", kind `.cash`, so the mapping is picked once and remembered); currency exchange →
    `.transferHalf` with the foreign amount (parsed from the title) as `transit`.
  - Dates: settled rows `occurredAt` = booking date (`Data operacji`, as R-IMP-PKO-2 says the
    booking date wins), `valueDay` = `Data waluty`; holds use the value date for both.
  - Description = merchant, else counterparty name (title → note), else title.
  - `original` only when the merchant currency differs from the account's (R-CUR-4).
  - `counterpartyIBAN` = recipient/sender account, spaces removed (R-IMP-PKO-3).
  - Fingerprints via `Fingerprint.pko`: settled rows `[booking date, value date, amount,
    balance, trimmed non-empty detail columns…]`; holds `["hold", value date, amount, Tytuł]`.
    A row repeated verbatim in one file gets a derived fingerprint and a warning.
  - File currency ≠ account currency → one file-level warning. Unreadable amount/date → row
    skipped with a line-numbered warning (`skippedRowCount`).
- Synthetic Windows-1250 fixtures `Fixtures/pko/all-types.csv`, `settled-later.csv` (README
  describes them).
- Tests: `PKOParserTests.swift` (22 tests, names cite R-IMP-PKO-1/2/3, R-IMP-3, R-CUR-2/4,
  R-TX-4), `PKORealDataTests.swift` (`.realData`, enabled when a `pko*` file exists).
- Verified: `swift test` green (all targets); real export: 79 rows, all parse, no warnings,
  unique and stable fingerprints — expense 73, income 3, transfer 2, transferHalf 1;
  pending 2; refunds 0; with original amount 0; with counterparty account 12. App builds.

## Blockers / contract-change requests (for the orchestrator)
None blocking. Suggestions:
1. **Explicit row hint (optional).** ATM withdrawals and currency exchanges are encoded with
   existing fields (`.transfer` to the external "Cash" account; `.transferHalf`). If A6 prefers
   an explicit marker, add e.g. `NormalizedRow.sourceHint: { atmWithdrawal, currencyExchange }`.
2. **Minor-unit digits for any ISO code.** `OriginalAmount.minorUnits` needs the currency's
   decimals (JPY 0, KWD 3, …). `PKOAmount.minorDigits(currencyCode:)` holds a local table; A3
   needs the same — worth moving to `AbacusDomain/Model/Money.swift`.
3. **For A6:** `counterpartyIBAN` is the number as printed without spaces (Polish NRB, 26
   digits, no `PL`). Normalise `Account.iban` the same way (strip spaces, drop a leading `PL`)
   before comparing.
4. **Doc alignment (pko-format.md, orchestrator):** the fingerprint section shows a literal
   `pko:<account>:<dates>:…:<sha1>` key; the contract `Fingerprint.pko` hashes the account id
   and parts with SHA-256 instead (implemented that way, parts listed above).

## Spec gaps found in the real export (no real data quoted)
- `Oryginalna kwota operacji` carries **no currency code** in the real file (all rows were in
  PLN): `…: 17.35`, not `…: 17.35 PLN`. The format for a foreign purchase is unverified; the
  parser accepts an amount with an optional trailing 3-letter code, and warns when there is no
  code and the amount differs from the charged one.
- Some keys carry a spreadsheet quote prefix: `'Operacja: …` (BLIK web payments, ATM).
- Detail values have leading/trailing spaces; merchant addresses can contain runs of spaces;
  web merchants have only `Adres` (no `Miasto`/`Kraj`).
- A hold's `Tytuł` has a different shape from a settled card payment's (a letter followed by
  digits vs digits only), so the title will almost certainly not match on settlement — matching
  must rely on merchant, value date and amount (as the spec already says).
- Currency exchange (`WYMIANA W KANTORZE - UZNANIE`): sender = the PKO currency account (its
  account number is set as `counterpartyIBAN`); the title holds both legs:
  `FX<ref> USD/PLN <rate>  <amount> PLN -<amount> USD`, thousands separated by no-break spaces,
  comma decimals. The debit-side type name (in the currency account's export) is unseen; the
  parser matches any `WYMIANA W KANTORZE` type and takes the direction from the sign.
- `Przelew na telefon przychodz. zew.` rows were all outgoing despite the name; the sign decides.
- Card payments are booked 1–3 days after `Data waluty`. **Owner question:** date settled card
  payments by the booking date (now, per R-IMP-PKO-2) or by the purchase day (`Data waluty`)?
- The file has 79 data rows (80 lines with the header); rows are not strictly newest-first
  (holds sit among dated rows). The parser does not rely on order.
