# C35 — Import: refund suggestion
State: done (awaiting merge)   ·   Branch: wp/C35-import-refund-suggestion   ·   Updated: 2026-10-30

Owner-approved: during import an incoming row that looks like the refund of an expense is offered as
one, using the refund API of C30 (`docs/status/C30.md`, "Import suggestion proposal").

## Behaviour
- **Which rows.** A NEW row (status New, no review decision) that is money in, has no attached records
  and is not a transfer or a debt record: an income row (e.g. an incoming bank transfer) or an expense
  marked as refund (a PKO card refund). Rows already imported, possible duplicates, settled holds,
  skipped rows and outgoing rows are never offered. A row the user turns into a transfer or a debt
  record stops being eligible at once.
- **Suggestion rule (kept as C30 proposed).** Top candidate of
  `RefundRepository.refundCandidates(probe:matching:limit:)` with `isSameAmount` and `score >= 70`
  (same description + same amount; C30's window: expense up to 60 days before the refund, not after;
  fully refunded expenses and expenses smaller than the refund are not candidates). Only in the row
  account's currency. No looser rule: a looser one (contains-match, 63 points) would offer unrelated
  shops; "Choose another…" covers the rest.
- **On the row** (Transactions tab): "Looks like a refund of <payee> · <dd.MM.yyyy> · <amount>" with
  Accept, Choose another…, Not a refund. Accepted: "Refund of …" with Change…, Not a refund; the row
  shows "New refund" and "Category follows the expense" instead of a category picker. After "Not a
  refund" the row is an ordinary income row with a quiet "Not a refund · Undo"; the suggestion never
  reappears on the same preview (decision kept across every recompute, account remap included).
- **Choose another…** reuses C30's `RefundPickerSheet`/`RefundPickerModel`: search over the existing
  expenses (60-day window until a search text is typed) and over the expenses of the same file; options
  that would exceed the expense or are in another currency are not listed.
- **Accept** turns the row into an expense refund (`type .expense`, `isRefund`, money still comes in,
  balances as for an income) in the original's category, same convention as C30's "This is a refund
  of…". The row's own category pick, a file category or a rule no longer apply, and no rule is learned
  from it (`rulePattern` nil, skipped by rule learning, never in the C31 rule-suggestions sheet). The
  C31 bulk bar gets no new action; a refund row has no category cell, so a bulk Category skips it.
- **Same file.** A purchase and its refund in one file work in either row order: the refund row's
  `refundOf` is `.row(<purchase row id>)`. The expense must be a new, non-refund, non-debt expense on
  the same account/currency. Its category is whatever that row ends up with (file, rule, user pick,
  learned rule) and is copied after rule learning. If the user later skips it, turns it into a
  transfer or a debt record, the accepted choice becomes invalid and the refund row is an ordinary
  income row again (the choice comes back if the purchase is included again).
- **Cap.** Several rows may be accepted for one expense while together they do not exceed what is
  open; the refused one stays as it was (`acceptRefund` returns false, the wizard shows a message).

## Design decisions
- **Link at insert, not `linkRefund` after the batch.** The new transaction is inserted with
  `refundOfID`, `isRefund`, type expense and the original's category in the same database transaction as
  the rest of the import (`CommitBuilder` assigns row transaction ids up front, so an expense of the same
  file can be the target whatever the order). `ImportStore.commit` validates every such link before
  `RefundLinks.repair` (the original must still be a refundable expense, `RefundRules.checkCap` with
  no rates, so only same-currency sums are compared) and refuses the whole import with a `RefundError`
  otherwise. Reason: one atomic commit, no half-state when a link fails, nothing extra to undo.
  `linkRefund` itself is not called by the import; its rules (`canBeRefund`, `canBeOriginal`,
  `checkCap`) are the ones used.
- **Undo.** Undo deletes the batch's transactions; `RefundLinks.repair` (already in `ImportStore.undo`)
  clears a link whose original was in the batch: a refund imported in a *later* batch stays an
  unlinked expense refund with its category (tested). Undoing the refund's own batch leaves the expense
  untouched. **Re-import:** the refund row carries its normal fingerprints, so it is "Already imported"
  and never offered again.
- **Where the logic lives.** `AbacusImport/Pipeline/ImportRefunds.swift` (`RefundMatcher`,
  `ImportPreview.acceptRefund/declineRefund/resetRefund/fileRefundOptions/refundProbes`), resolver pass
  `applyRefunds` + `finishRefundCategories` in `ImportPreview.swift`, `ImportPipeline.refunds`
  (optional `RefundRepository`, set by `ImportWizardDependencies.live`; nil in fakes = no suggestions
  among existing expenses) with `refundOptions(for:row:matching:limit:)`. Existing-expense suggestions
  are looked up once per eligible row when the preview is built and after an account remap (read-only,
  cached in `existingRefundSuggestions`); expenses of the file are matched on every recompute from an
  (account, amount) index, so edits stay cheap. Feature layer: `ImportRefunds.swift`
  (`ImportRefundItem`, `ImportRefundPicker`, wizard actions, picker candidate source).
- `ImportSummary.refundsLinked` and a line "N linked as refunds of expenses" on the Done screen.
- The headless `abacus-import` tool is unchanged (no refund repository: nothing is offered, nothing
  accepted by `acceptingDefaults`).

## Limitations
- The headless tool never links refunds.
- A refund in another currency than the expense is not suggested or listed (the cap needs a rate and
  the store check is lenient without one).
- Rows that go into a *new* account (file-created) can only match expenses of the same file.
- An existing expense that another row of the same import settles, links or converts is not offered
  as an original.
- The Done screen says how many were linked but does not list them.
