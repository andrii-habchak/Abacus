# C48 — Moved import batch: visible in the target account, and a "Moved from" trace

State: done (awaiting merge)   ·   Branch: wp/C48-moved-history

Owner report: after History > Move to another account he "doesn't see the import transaction movement in
the account history".

## (a) Rows, balances, caches — no bug found, now covered by tests
Test over the real repositories and a real `AppSession` (`ImportMoveHistoryTests`): after a move the list
query filtered by the target account returns every moved transaction, the source returns none, balances
follow (source 0, target = old source), the list summary counts them. The wizard's `onDataChanged` is wired
to `AppSession.dataChanged()` (RootView), which reloads Transactions, Accounts, Dashboard and the manage
screens; the test checks the Transactions rows, the Accounts balances and the Dashboard after it. Nothing was
stale. The likely reason for "not seen" is (b): nothing on a moved transaction said it had moved.

## (b) Trace — done (schema v17)
- Table `txnMoves` (id, txnID CASCADE, batchID SET NULL, fromAccountID, toAccountID, movedAt); no UNIQUE,
  accounts are plain ids (CloudKit rules). `AbacusDomain/Model/TxnMove.swift`, migration in `Schema.swift`.
- `SQLiteImportStore.move(... at:)` writes one row per moved transaction in the same database transaction.
  Moving a transaction back to the account its latest trace came from deletes that trace instead (Undo move
  leaves nothing; A→B→C says "from B"; C→B again says "from A"). Undo import deletes the transactions, the
  traces go with them (CASCADE).
- `SQLiteImportStore: TxnMoveReading.moves(for:)` (latest per transaction).
- Transactions list: grey badge "Moved from <account>", hover "Moved from A to B · 1 Nov 2026"
  (`TransactionsViewModel(moves:)`, `Row.movedNote`, badge kind `.moved`). Editor: a hint line under the
  header (`TransactionEditorModel.movedNote`, `TransactionEditorDependencies.moves`). Wired in `AppSession.live`.
- Source side shows nothing (the rows are gone from it).

## Found on the way (not fixed)
`TransactionFilters.allDates` has its upper bound at 9999-12-31; `DayBounds.end` makes it 10000-01-01, which
sorts before "2026-…" as text, so with a **UTC/GMT calendar** the "all dates" filter returns nothing. A
positive-offset zone (Warsaw) is unaffected, so the owner does not see it. Tests use a 2000–2100 range.
